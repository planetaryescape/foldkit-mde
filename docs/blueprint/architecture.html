packages/core/src

State and pure transformations

  • editor.ts: Schema Model/Message, init, exhaustive update, transaction application, undo/redo.
  • bold.ts: Selection/Transaction schemas and pure bold range replacement.
  • markdown.ts: small paragraph/bold parser, raw-block fallback, source ↔ visual offsets.

packages/editor/src

  • view.ts: toolbar, modes, status, mount point; exports view and Synchronize.
  • surface.ts: Observe mount, scoped listeners, message emission, composition, paste, keyboard shortcuts, synchronization command.

  • editor.css: reusable editor appearance, separate from playground styling.

packages/plugins/src

Concrete output formats

json.ts declares the versioned JsonDocument Schema and implements json.project(source) with core parsing.

There is no HTML or custom-component implementation here yet. Bold currently lives in core, not in this workspace.

03 / State machine, not another runtime

Source is the fact. Everything else has a defined role.

packages/core/src/editor.ts / Model shape
Model {
  source: string
  selection: { start: number, end: number }
  mode: 'Visual' | 'Markdown'
  past: readonly { source, selection }[]
  future: readonly { source, selection }[]
}

The invariants

  • update(model, message) is the document writer. It returns the next Model without mutating the previous one.
  • Selection uses Markdown source offsets, not visible character counts. Ranges are end-exclusive.
  • Source-changing edits snapshot source + selection and clear redo.
  • Mode and selection changes do not add history entries. Undo/redo do not restore mode.
  • Parsed blocks, rendered DOM, and JSON nodes are derived. The browser temporarily mutates DOM during input; the adapter commits the result through messages.
Message Where it comes from Core transition
UpdatedSource Textarea or DOM read after input Replace source + selection; add history only if source changed.
Selected DOM selectionchange / beforeinput Update source offsets only.
Applied Paragraph split or a formatting caller Replace [start, end) with transaction text and select its resulting range.
ToggledBold Toolbar / keyboard Call the directly wired bold operation, then apply its transaction if supported.
ChangedMode Mode controls / Edit source Change mode without rewriting Markdown.
Undo / Redo Toolbar / keyboard / browser history input Move source + selection snapshots between past and future.
Synchronized Completed Synchronize command No state change.

Schema defines value shapes; Match checks exhaustive handling. This is our reducer-based machine, not XState or an extra actor system. External JSON still needs explicit decoding.

04 / Runtime control flow

Follow one edit through the actual calls.

Special input paths

  • Enter: beforeinput calls split, prevents the default, and emits Applied.
  • Paste: insert a plain text node, then read and dispatch. Source HTML is never injected.
  • Composition: pause input dispatch while composing; commit on compositionend. Real OS IME is still unverified.
  • Unsupported syntax: show an opaque card. Edit source changes mode at its source offset.

Effect and Foldkit each have a job

  • Effect Schema + Match: declare state/events and pure transitions.
  • Effect.acquireRelease: acquire browser listeners in Observe and remove them when the mount scope ends.
  • Stream + Queue: turn DOM callbacks into Foldkit messages.
  • Foldkit Mount / Command / Runtime: own observation, DOM synchronization, and the application loop.
05 / Extension boundaries

Plugins either describe an edit or derive an output.

Existing interface + bold operation

Formatting

interface FormattingPlugin {
  readonly id: string
  readonly apply: (
    source: string,
    selection: Selection
  ) => Transaction | undefined
}

A pure function describes a replacement. undefined means the operation does not support that selection. Core applies the transaction and owns history. 

Transaction {
  start: number
  end: number
  text: string
  selection: { start: number, end: number }
}

Replace the source slice [start, end) with text. Selection refers to the resulting source. This is a range replacement, not a second document or an AST mutation.

Bold is still called directly by core and toolbar. There is no plugin dispatch table, registration, or plugin-defined toolbar yet.

Existing interface + JSON implementation

Representation

interface Representation<Output> {
  readonly id: string
  readonly project: (source: string) => Output
}

The caller supplies source and receives an output. JSON does not own state, apply edits, or start Effects.

JSON is version 1: exact source, Paragraph children with text/bold, Raw nodes with source, and source spans. The parser is a small supported subset, not CommonMark.

Planned / no exported API

HTML representation

Fits the read-only projection role. It needs a supported-syntax policy, escaping, and a decision about trusted HTML before implementation.

Likely owner: a format module in packages/plugins/src. No HtmlOutput type or renderer exists today.

Planned / contract undecided

Custom components

Need syntax recognition, source-preserving edits, and a browser node adapter. A read-only representation interface cannot cover those jobs alone.

Core should own neutral syntax/transaction contracts; the editor should own DOM adapters; gbfm should supply music/media behavior and services.

JSON import is a separate editing feature. Schema decoding checks the declared shape, not consistency between source and nodes. Import must choose one authority, validate semantic constraints, and produce core transactions. We do not implement that path yet.
06 / Consumer recipes with today's exports

Use the core alone, or assemble a Foldkit application.

These examples use existing APIs. There is no imaginary registration or widget factory hidden in the examples.

Code keeps its original line breaks. Scroll a code block sideways if it is wider than the screen.

A / Headless edit + JSON / runnable Bun TypeScript
import { bold, init, Message, update } from '@foldkit-mde/core'
import { json } from '@foldkit-mde/plugins/json'

const model = init('A long track.')
const transaction = bold(model.source, { start: 2, end: 6 })

const next = transaction
  ? update(model, Message.cases.Applied.make({ transaction }))
  : model

const output = json.project(next.source)
console.log(JSON.stringify(output, null, 2))

What this produces

source: 'A **long** track.'
selection: { start: 4, end: 8 }
past.length: 1
future.length: 0

JSON:
  version: 1
  source: 'A **long** track.'
  nodes[0]: Paragraph
    span: { start: 0, end: 17 }
    children:
      { text: 'A ', bold: false }
      { text: 'long', bold: true }
      { text: ' track.', bold: false }

This needs no DOM, Foldkit runtime, or editor package. Source spans use JavaScript string offsets.

B / Minimal main.ts without local saving
Original editing-only composition / complete browser entry
import { init, Model, type Message, update } from '@foldkit-mde/core'
import { Synchronize, view as editorView } from '@foldkit-mde/editor'
import { json } from '@foldkit-mde/plugins/json'
import { Runtime } from 'foldkit'
import type { Document, HtmlBuilder } from 'foldkit/html'

const view = (model: Model, h: HtmlBuilder<Message>): Document => ({
  title: 'My Markdown editor',
  body: h.main([], [
    editorView(model, h),
    h.pre([], [JSON.stringify(json.project(model.source), null, 2)]),
  ]),
})

Runtime.run(
  Runtime.makeApplication({
    Model,
    init: () => ({ model: init('A long track.'), commands: [] }),
    update: (model, message) => {
      const next = update(model, message)

      return {
        model: next,
        commands:
          next.source !== model.source || next.mode !== model.mode
            ? [Synchronize({
                source: next.source,
                mode: next.mode,
                selection: next.selection,
              })]
            : [],
      }
    },
    view,
    container: document.getElementById('root'),
  }),
)

Consumer call tree

main.ts
└── Runtime.run(makeApplication(...))
    ├── init(source) → initial Model
    ├── view(model, h)
    │   ├── editorView → Observe mount
    │   └── json.project(model.source)
    └── update(model, message)
        ├── core.update → next Model
        └── changed source/mode?
            └── Synchronize → browser DOM

import type { FormattingPlugin } from '@foldkit-mde/core/plugins'

export const boldPlugin: FormattingPlugin = {
  id: 'bold',

07 / Intended integration, not shipped integration

gbfm supplies the product. The library supplies editing.

Host responsibilities

  1. Load canonical Markdown and initialize editor state.
  2. Translate child editor messages through the host's Foldkit update path.
  3. Configure the editor-owned local-saving integration with identity, policy, and a storage Layer. Observe typed output for backend saving or publishing. Model changes and projections are not durable receipts.
  4. Keep publishing, auth, uploads, Spotify, and network failures in host services.
  5. Supply music/media syntax and visual adapters when the custom-component contract exists.

This list is the intended ownership, not working gbfm integration code. No gbfm files or production behavior change in this repository.

What must change before clean embedding?

  • Instance identity: view and Synchronize use the fixed mde-surface ID. Multiple editors are not supported.
  • Parent composition: the view is typed to core Message. A child-message mapping/output boundary has not been packaged.
  • Plugin routing: replace direct bold wiring with host-selected actions, without moving history into plugins.
  • Syntax coverage: headings, lists, links, music/media nodes, and complete formatting semantics remain outside the editable subset.
  • Packaging: build/publish policy and an external consumer contract remain undecided.

Keep source authoritative while adding plugin dispatch and instance-scoped mounting. Do not introduce another JSON document store or a separate plugin runtime to solve embedding.

09 / Implemented local-saving extension

The editor owns saving. The host chooses storage.

Markdown remains authoritative. IndexedDB holds the last committed checkpoint, not a second editable document. JSON remains a projection. The host supplies identity, seed, policy and Layer; the integration supplies loading, autosave, status, retry, flush and recovery.

Integration and consumer files

  *.test.ts       public contract / lifecycle tests

apps/playground/

  test/persistence-check.js reload / conflict / recovery
Consumer API: Editor.make({ key, seed, policy }) supplies the complete integration. Editor.project(model, markdown | json) returns typed content and its local revision, not a save receipt. Follow the compiled playground composition or the current usage guide.

What commits

Seed only when missing, including empty source. 500 ms quiet / 2 s maximum dirty-window policy in the playground; 1 MiB UTF-8 limit. A receipt is emitted only after transaction completion. Session, local revision, key and write ID guard stale results. Unknown outcomes retry the exact old write.

What stays safe

Conflicts stop automatic writes and preserve local edits/export. Failed loading pauses editing. Recovery previews/exports the previous checkpoint without overwriting the unreadable original. Retention permission is separate from Saved locally. Export valuable work.

Verified through native browser transactions and two independent runtimes: competing writers, aborted writes after request success, malformed/future rows, reload, empty recovery and conflict UX. No journal, durable undo, SQLite, switching, catalog, deletion, remote save or gbfm integration. Browser scheduling and storage retention are not crash-loss guarantees.

This is an implementation map and a consumer guide, not a claim of full WYSIWYG, a published library, or completed gbfm integration.
